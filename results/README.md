# CUDA performance results

Latest run of each workload's current implementation at the largest problem size tested (dominant kernel, if one dominates, and the whole application) on each GPU, generated by `build_spreadsheet.py` from measurements and profiles committed in this repo. Each GPU's binaries and profiles live in its own folder (`rtx3090/`, `rtx4090/`); the sources are shared. The spreadsheet [`cuda_performance.xlsx`](cuda_performance.xlsx) has one sheet per GPU plus the ncu metrics of every profiled launch. Lower times are better.

Each workload runs three ways, left to right: **Direct** (the kernels and copies enqueued directly on every iteration, without a CUDA Graph), **CUDA Graph** (the same work captured once and replayed) and **Agentic optimized** (formerly SOTA; `<name>_sota.cu`): the fastest implementation found after researching published libraries and kernels, free to change kernels and data movement and launched whichever way is fastest. It does the same work per iteration: every timed iteration copies the full input from the host and the full output back, and it rotates over 3 different inputs and checks every output, so caching across iterations would fail (llama2c's inputs stay on the GPU in all versions). Outputs match the Direct and Graph versions (each workload's `compare_sota.sh`).

Each version has three times:

- **Full batch** (ms): one batch of back-to-back iterations between CUDA events (`time_all.sh`: 50 iterations).
- **Per iteration** (us): full batch / iterations.
- **Single iteration** (us): median of 20 iterations, each launched alone on an idle device. The device is drained before each, so the iteration's launch cost is exposed instead of overlapping the previous iteration's work as it does in the batch.

**Single / batch** = single iteration / per iteration in the batch: how much launch cost batching amortizes in each launch mode. **Graph speedup** = Direct / Graph and **Agentic speedup** = Graph / Agentic optimized, for the full batch and for a single iteration. Kernel rows have one ncu time per version (a single launch replayed in isolation), so they fill only the single-iteration columns; their agentic speedup compares the ncu time of all the kernels doing that row's work in one iteration (see the spreadsheet notes). — = not applicable.

### How the predicted speedup is calculated

The predicted speedup uses only the RTX 3090's ncu reports and the two GPUs' published specs (RTX 3090: 82 SMs, 1.695 GHz boost, 19.5 Gbps GDDR6X; RTX 4090: 128 SMs, 2.52 GHz boost, 21 Gbps GDDR6X; both 384-bit, PCIe 4.0 x16), so it is fixed before any 4090 measurement. Each unit's peak scales by its hardware ratio: SM compute by SMs x SM clock, L1/L2 cache throughput assumed to scale the same way, DRAM by memory data rate (the 3090's own SM and memory clocks come from its ncu report: 1.69 GHz and 18.98 Gbps, so the ratios are about 2.32x and 1.11x).

Kernel rows: ncu gives each launch's SM, memory (L1/L2) and DRAM throughput as a percent of the 3090's peak. Keeping the work per unit fixed, a unit at u% that is r times faster needs u/r% of the old time, and the slowest unit sets the new time: speedup = max(u) / max(u / r). So a DRAM-bound kernel gets ~1.11x and a compute- or cache-bound one ~2.32x. A launch below 60% on every unit is latency-bound and gets the SM clock ratio (1.49x). A kernel with several launches combines them weighted by time.

Whole-application rows: the kernels in that workload's ncu report (one run of the application) scale by their predicted speedups; the rest of the 3090 time (H2D/D2H copies over the same PCIe 4.0 link, launch gaps) is assumed unchanged. Where the kernels overlap (llama2c's three streams; their summed time exceeds the iteration time), the whole time scales with the kernels.

Not modelled: cache capacity (the 4090's L2 is 72 MB vs 6 MB, so data that spilled to DRAM on the 3090 can stay in L2), kernels overlapping copies (pagerank's first iteration), clocks above rated boost, and compiler differences (CUDA 13.3 vs 12.5). Measured = 3090 time / 4090 time for the CUDA Graph column; kernel rows read pending until the 4090 ncu reports exist.

- llama2c (coalesced matmul) / matmul_coalesced_kernel: **1.11x**. DRAM-bound (DRAM 94% busy; SM 5%, L1/L2 94%): data rate 21 / 18.98 Gbps = 1.11x.
- llama2c (coalesced matmul) / Whole application (rmsnorm + softmax + matmul iteration): **1.11x**. Kernels overlap (their summed ncu time is 105% of this time), so all of it scales with the kernels' 1.11x.
